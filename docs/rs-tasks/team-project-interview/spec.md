## Что сдаётся

У пары один общий проект. Каждый студент сдаёт свою работу отдельно.

Нужны все пункты:

- работающее приложение по ссылке;
- общий репозиторий;
- доска задач со ссылкой;
- у Дмитрия (GitHub `Bogagree`) свой Pull Request в `main` общего репозитория;
- в ветке этого PR файл вроде `submissions/Bogagree.md`;
- в файле и в описании PR одно и то же: имя или логин Дмитрия и напарника; что делает приложение и какие задачи делал Дмитрий; ссылка на деплой, репозиторий и доску; ссылка на интервью, где Дмитрий — кандидат;
- PR не мержить до конца проверки;
- ссылку на свой PR отправить в RS App → Cross-Check: Submit до дедлайна курса. В работу по этому плану Submit не входит: его делает Дмитрий сам.

Проверяющий смотрит запись, где автор PR — кандидат. Проект он не запускает и дизайн не оценивает. Ссылки нужны как контекст. Если доска закрыта, её содержимое должно быть видно на записи.

Репозиторий общий, свой, не форк школьного репозитория. В гайде его создаёт один из пары и приглашает второго как collaborator. Для этого плана владелец — `Bogagree`, имя репозитория из гайда — `team-store` (пару имя можно сменить до шага 1). Репозиторий в гайде публичный.

## Стек

README не запрещает конкретные библиотеки. Технологии выбирают такие, которые знакомы обоим. Рекомендация README: TypeScript и Jest или Vitest.

Этот план идёт путём гайда, потому что он совпадает с рекомендацией:

- Vite, шаблон `vanilla-ts`;
- Vitest, команда `npm test`;
- данные товаров в файле проекта, без своего сервера и без внешней базы.

Внешний API, свой сервер и дополнительный интерфейс README разрешает по желанию. В этот план они не входят.

Гайд запрещает публиковать в репозитории токены, пароли и другие секреты.

## Ветка, имя PR, дедлайн

- Общая ветка проекта: `main`.
- Задачи делаются в отдельных ветках. Гайд показывает вид `feature/<задача>`. PR из такой ветки в `main`, напарник смотрит изменения, после этого PR мержат.
- Сдача Дмитрия: отдельная ветка от `main` после слияния нужных изменений проекта. В README точное имя ветки не задано. В плане ветка называется `submission/bogagree`.
- Имя PR в README не задано.
- PR сдачи открывается в `main` и остаётся открытым до конца проверки.
- Дата дедлайна в README, гайде и `cross-check.json` не указана. В тексте только «до дедлайна».

## Поведение для пользователя

Минимум магазина из README.

1. При загрузке открывается страница «О нас»: что делает приложение, участники (имя или GitHub-логин) и краткий вклад каждого.
2. Пользователь видит список товаров. Данные лежат в проекте.
3. Пользователь добавляет товар в корзину.
4. Пользователь удаляет товар из корзины.
5. Пользователь видит общую стоимость выбранных товаров.

Чтобы и стартовая страница, и эти действия были доступны, с «О нас» есть переход к списку и к корзине и обратный переход. Это способ выполнить оба требования README, без поиска, фильтров и сортировки из гайда.

README не задаёт повторное нажатие «в корзину» для того же товара. Рабочее правило плана, чтобы сумму можно было проверить: у товара одна строка, повторное добавление состав корзины не меняет. Пустая корзина даёт сумму 0.

Отдельная функция с понятным результатом нужна для unit-тестов на интервью. В плане это функция общей стоимости: на вход строки корзины с ценой, на выход сумма. Запуск тестов готовится заранее. Тесты, которые попадут в оценку live coding, пишутся во время записи. Если тесты уже есть, на записи добавляют новые сценарии, старые не удаляют.

## Интервью

Два отдельных разговора, затем смена ролей. Ориентир 15–30 минут. Для сдачи Дмитрия считается запись, где он кандидат, а напарник интервьюер.

Запись: голоса обоих слышны, на экране читаются приложение, код и результат тестов. Камера не обязательна. Видео размещают так, чтобы человек вне команды открыл его без входа и без запроса доступа (в README примеры: YouTube по ссылке или Google Диск с просмотром для всех, у кого есть ссылка). Ссылку проверяют в режиме инкогнито.

Ход записи из README:

1. Знакомство: кто кандидат, что изучает и чем занимается.
2. Проект и команда: показать приложение и кратко объяснить назначение; показать доску и репозиторий; как планировали задачи, как общались и как делали ревью; какие задачи кандидат делал сам.
3. Вопросы. Все вопросы из README задавать не нужно, несколько подходящих достаточно. Можно добавить свои и уточнять ответы. Кандидат говорит о конкретных ситуациях, своих решениях и результате. Список в README:
   - какую задачу делал лично и как к ней подошёл;
   - с какой сложностью столкнулся, как нашёл причину и что помогло;
   - какое решение выбирал из нескольких вариантов, почему этот и от чего отказался;
   - как проверял, что функциональность работает;
   - как команда распределяла задачи и что было, когда планы менялись;
   - были ли разные мнения и как пришли к общему решению;
   - замечание на code review: что предложили изменить и почему;
   - что улучшил бы при большем времени и почему.
4. Live coding, ориентир 7–10 минут. Кандидат показывает функцию суммы корзины и несколько сценариев, объясняет назначение и ожидаемое поведение, предлагает варианты проверки. Во время записи пишет несколько содержательных unit-тестов, запускает их и объясняет результат. Если тест не прошёл, показывает результат и объясняет, как будет искать причину: в README оценивают ход рассуждений и действия, а не только успех с первой попытки.

Напарник сдаёт свою запись и свой PR отдельно. На той записи Дмитрий — интервьюер.

## Командная работа

Из README, без добавленных ритуалов:

- доска в Jira, GitHub Projects или аналоге; на задачах есть ответственные и движение по статусам, например «Запланировано», «В работе», «На ревью», «Готово»;
- общий репозиторий, договорённость о ветках, коммитах и слиянии;
- задачи в отдельных ветках, PR, взаимный просмотр и обратная связь;
- если распределение задач меняется, доску обновляют;
- заранее договариваются о времени встреч, канале связи и о том, что делать, если кто-то задерживается;
- работа разделена так, чтобы оба могли рассказать о своём вкладе.

Если напарник не выходит на связь, Дмитрий заранее пишет организаторам курса и согласует, как продолжать. Интервью тогда можно провести с другим участником курса или волонтёром, рассказывая о своём вкладе.

## Критерии и штрафы

Предлагаемый максимум в README — 300 баллов. Там же сказано, что баллы и формулировки пока можно обсудить. В `cross-check.json` уже стоят те же четыре пункта. Все пункты оцениваются по видео.

- Знакомство — 30. Кандидат представился и кратко рассказал о себе и обучении.
- Проект — 100. Кандидат показал приложение, доску и репозиторий, объяснил назначение проекта, свой вклад и то, как команда распределяла задачи и проводила ревью.
- Вопросы — 70. Интервьюер задал вопросы о проекте; кандидат рассказал о конкретной сложности или решении, рассмотренных вариантах, причине выбора и результате.
- Live coding — 100. Кандидат объяснил функцию и сценарии проверки, написал тесты во время записи, запустил их и разобрал результат.

Отдельных числовых штрафов в README нет. Пункт нельзя подтвердить, если видео недоступно, нельзя установить, кто кандидат, либо звук или изображение экрана не позволяют проверить этот пункт. Учитывается только то, что показано или объяснено на записи. Качество речи, акцент и оформление проекта на баллы не влияют.

## Что не входит

- Submit в RS App.
- Мерж PR сдачи до конца проверки.
- Вариант 2 (свой проект), пока Дмитрий не заменит этот план.
- Пример из гайда сверх минимума README: 8–12 товаров, категории, картинки, поиск, фильтр категории, диапазон цены, сортировка, сброс фильтров, количество «+» и «−», промокод, `localStorage`.
- Оплата, регистрация, настоящий сервер и база данных. Гайд говорит, что для примера магазина они не нужны.
- CI, ESLint и Prettier. В гайде это рекомендуемый способ работы, не баллы.
- Отдельные баллы за кнопки, дизайн или число возможностей. README их не даёт.
- Запуск проекта проверяющим.
